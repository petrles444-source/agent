# ThinkingAgent — автономный субагент-советник «Мышление»

> **Коротко: как запустить за 2 минуты → `docs/БЫСТРЫЙ_СТАРТ.md`**
> Colab → `Run all` → скопировать `THINKING_URL` и `THINKING_TOKEN` → на ПК
> `set-url` и `doctor`. Полная документация — ниже.

ThinkingAgent — автономный субагент-советник, который помогает в планировании и
рефлексии задач. По сути, это «второй мозг» для основного агента или разработчика,
работающий на бесплатных облачных ресурсах.

Нейтральный помощник **для любого главного агента**: LLM работает на Google Colab
и советует, как распланировать задачу, структурирует работу и рефлексирует после
шагов. На ПК — только стандартная библиотека, никаких зависимостей. Проект (игра,
сайт, скрипты) не важен — субагент работает с тем контекстом, который ему передали.

Позвольте рассказать, что это, как устроено, что уже реализовано и почему я считаю
проект интересным с инженерской точки зрения.

---

## 🎯 Что это и для чего нужно

ThinkingAgent — это проектонезависимый субагент, который:

* разбивает нетривиальные задачи на шаги с ожидаемыми результатами и зависимостями;
* проводит рефлексию после каждого шага и корректирует план;
* ведёт диалог с человеком через веб-панель;
* хранит историю, память и метрики между сессиями.

**Ключевая идея:** тяжёлая LLM живёт в Google Colab (бесплатно), а на ПК — только
стандартная библиотека Python. Это даёт мощь облачной модели без затрат на локальное
железо и без установки зависимостей на клиенте.

**Кому это нужно:**

* **основному агенту** — как второе мнение перед началом работы: план,
  критерии, список противоречий и рисков до того, как что-то сломано;
* **разработчику** — как структурный помощник: разбить большую задачу на шаги,
  получить рефлексию «что пошло не так» и скорректировать курс;
* **CI/скриптам** — предсказуемые коды выхода (`0/1/2/3/4/5`) и JSON-контракты,
  результат встраивается в пайплайн без парсинга прозы.

## 🧩 Как это работает

Один рабочий цикл выглядит так:

1. **Задача.** Человек или основной агент формулирует нетривиальную задачу —
   `plan "…" --files a.py,b.py --stream`. Субагент не читает файлы сам: весь
   контекст (`--files`, `--constraint`, `--context`) ему передают явно,
   неизвестные пути он честно вернёт в `unknown_files`.
2. **План.** LLM на Colab разбивает задачу на шаги: у каждого — действие
   (`build/test/refactor/verify/docs/prompt/debug/release`), ожидаемый результат,
   критерии успеха и зависимости; отдельно — найденные противоречия.
3. **Работа.** Основной агент выполняет шаги; тем временем мысли и события
   стримятся по SSE в веб-панель — вкладки «Связь агентов» и «Отчёты» обновляются
   в реальном времени.
4. **Рефлексия.** После шага — `reflect ID --step N --result "…"`: субагент
   оценивает результат и возвращает статус — `ok` (идём дальше по плану),
   `adjust` (скорректировать курс) или `abort` (прервать работу); можно и
   `--async`, чтобы не блокировать основную работу.
5. **Память.** Диалог и факты складываются в `memory.json` (профиль, факты,
   последние 12 реплик + саммари старых), поэтому следующий запрос начинается
   не с нуля, а с учёта уже сказанного.
6. **Отказ.** Если Colab упал — вызов возвращается с `fallback=True`, панель
   честно показывает «заглушку», обрывы потока переживаются повторами, а работа
   не встаёт ни на секунду.

Всё, что произошло, пишется на диск (события, история, отчёты) — поэтому история
переживает перезапуски процессов и видна из любой сессии.

## 🏗️ Архитектура

Взаимодействие построено по классической клиент-серверной схеме:

```text
ПК (только stdlib)                          Google Colab (бесплатно)
┌─────────────────────────────┐             ┌──────────────────────────────┐
│ tools/thinking_cli.py       │   HTTP/SSE  │ llama_cpp.server (Qwen2.5-7B)│
│ tools/thinking_panel.html   │ ◄─────────► │ thinking_server.py (FastAPI) │
│ thinking/client.py          │             │ cloudflared (туннель)        │
│ thinking/fallback.py        │             └──────────────────────────────┘
└─────────────────────────────┘
```

На ПК:

* `thinking/schemas.py` — контракты и валидация JSON-схем (источник правды);
* `thinking/client.py` — синхронный клиент с повторами, таймаутами и fallback;
* `thinking/fallback.py` — заглушка, если Colab недоступен;
* `tools/thinking_cli.py` — CLI для управления и веб-панель.

На Colab:

* ячейки A–F: окружение, сборка FastAPI-сервера, запуск LLM и туннеля, фон,
  остановка; ячейка A кладёт **выбранный профиль моделей** (одна строка
  `PROFILE = "..."` в её коде), а не все сразу:
  | профиль | что качает | размер |
  |---|---|---|
  | **`dev`** | **3B + 1.5B + 7B; активна 3B — рекомендуется на CPU** | ~7 ГБ |
  | `light` | только 3B + 1.5B (по умолчанию для `PROFILE = "auto"` на CPU) | ~3 ГБ |
  | `gpu` | 7B + 3B + 1.5B (по умолчанию для `auto` на T4) | ~7 ГБ |
  | `strong` | Qwen2.5-14B + 3B — не для бесплатного Colab: замерено 0.05 ток/с (подкачка страниц), нужен RAM от 16 ГБ | ~10 ГБ |
  | `big` | Qwen3-30B-A3B + 3B — MoE: 30B параметров, активны 3B; при RAM 12.6 ГБ не поднялась | ~19 ГБ |
  | `coder` | Qwen2.5-Coder-32B + Coder-14B + 3B | ~27 ГБ |
  | `uncensored` | сборки без цензуры + обычная 3B | ~5 ГБ |
  | `all` | всё сразу — не советуем | ~60 ГБ |

  Запасная модель профиля всегда **заметно меньше** основной: откат нужен,
  чтобы спасти сессию при нехватке памяти, а модель того же размера в том же
  RAM не спасёт.

  **Почему `dev` качает 7B, если активна 3B.** 7B входит в профиль через
  `ALSO["dev"]`: он лежит на диске только для переключения во вкладке
  «Модели» (на T4 она отвечает в разы быстрее) и **в цепочку отката не
  входит** — откат обязан вести к меньшей модели. Поэтому ячейка A пишет
  два файла: `thinking_chain.txt` (активная + откат, его перебирает ячейка D)
  и `thinking_models.txt` (всё, что можно выбрать во вкладке «Модели»).
  До 04.10 дополнительные модели скачивались, но в `thinking_models.txt` не
  попадали — 4,7 ГБ лежали молча, а в переключателе их не было.
  Ячейка A печатает, что именно качает и сколько это мегабайт.

  **Сколько моделей держать одновременно:** на бесплатном Colab (2 ядра) суммарный
  поток токенов от нескольких моделей не растёт — ядра те же. Поэтому по умолчанию
  работает одна модель; `THINKING_PARALLEL` включает параллельные движки для сверки
  ответов (`ask-multi`), а на машине с GPU и 16+ ГБ RAM профиль `big`/`strong`
  включается сменой одной строки `PROFILE`.

  Переключение между скачанными моделями — во вкладке «Модели», подписи
  считаются автоматически (`1.5B-UNC` / `3B-UNC` / `7B-UNC` / `30B-A3B` /
  `32B-CODE`);
* `scripts/build_colab.py` — автоматическая сборка zip с исходниками и генерация
  готового ноутбука.

Принципы работы (субагент только советует, не блокирует работу, всё пишется на
диск, живой поток, честная выгода) — в §1.

## ✅ Что уже реализовано

### 🛡️ Отказоустойчивость

* **Fallback:** если Colab упал, клиент возвращает заглушку с `fallback=True` —
  работа не блокируется.
* **Повтор при обрыве SSE:** read-timeout 45 с, до 3 попыток; в чате панели видно
  «обрыв потока — повторяю… (1/3)», частичный текст очищается без дублей.
* **Запасной транспорт:** если поток не прошёл после всех попыток, клиент сам
  падает на не-потоковый `POST /chat` / `POST /dev` — короткие JSON-запросы
  проходят в «плохие окна», ответ в панели помечен «без потока».
* **Предохранитель (circuit breaker):** 5 ошибок подряд → пауза 10 минут вместо
  бесконечных ретраев по мёртвому туннелю.
* **Кэш ответов панели:** повторный тот же вопрос в течение 30 минут
  (`answer_cache_ttl`) — мгновенно и без нагрузки на Colab (живой замер:
  3.5 с → 1.0 с), ответ помечен «из кэша».
* **Прогрев сессии:** фоновый цикл панели дёргает `/health` раз в ~25 минут —
  Colab не засыпает между рабочими сессиями.
* **Диагностика потоков:** `docs/ДИАГНОСТИКА_ПОТОКОВ.md` — хронология обрывов SSE,
  матрица решений и runbook по восстановлению.

### 🧠 Память и контекст

* `memory.json` хранит профиль, факты и последние 12 реплик чата.
* В промт уходит срез: последние 12 фактов и 6 последних реплик, обрезанных
  по 300 символов.
* **Автосуммаризация диалога:** реплики, выпавшие из окна, не выбрасываются —
  сжимаются в одно саммари-факт «Саммари диалога: …», которое уходит
  в следующие запросы.
* Кнопки «Запомнить», «Стереть память», точечное удаление фактов в панели.
* **Дедупликация фактов:** точный дубль (после нормализации) не добавляется,
  пересекающийся факт заменяется более полным.
* **Экспорт/импорт памяти:** кнопки «Экспорт памяти» и «Импорт памяти» —
  `memory.json` скачивается файлом («поделиться памятью») и загружается обратно
  с проверкой лимитов.

### 💬 Веб-панель (9 вкладок)

* Отчёты, чат с субагентом, разработка, модели, диалог, токены, связь агентов,
  выгода и ускорение, журнал.
* `Enter` — отправить, `Shift+Enter` — новая строка; кнопка «Печать / PDF» —
  экспорт отчёта через диалог печати браузера (`@media print`).
* Чат не теряет сообщения: во время запроса история не перерисовывается поверх
  «в полёте», ошибка остаётся на видном месте.

### 📊 Наблюдаемость

* Токены: точные цифры из `usage` сервера или честная оценка по длине текста —
  с явной пометкой, что это оценка.
* KPI: среднее время ответа, срабатывания заглушки, графики.

### 🧪 Тестирование

* **607 офлайн-проверок** (`tools/thinking_test.py`) — контракты, фолбэк, кэш,
  предохранитель, саммари памяти, панель.
* Онлайн-проверки (`tools/thinking_online_test.py`) — связь, токен, метрики,
  реальный план от LLM, рефлексия.
* Коды выхода для CI: `0` — успех, `1` — провалы, `2` — сервер недоступен.

### 🚀 Автоматизация

* `scripts/build_colab.py` — одной командой собирает zip, заливает на tmpfiles,
  генерирует ноутбук с вшитой ссылкой.
* `scripts/build_bats.py` — пересборка `.bat`-файлов с UTF-8 без BOM и `chcp 65001`.

## 🔧 Что недавно исправлено

Я активно вёл диагностику обрывов SSE-потоков и внёс несколько важных фиксов:

* **Панель держала соединение после `done`** — браузер ждал EOF, сервер ждал
  следующий запрос. Исправлено: `Connection: close` + завершение по событию `done`.
* **Дедуп буфера событий** — окно дедупа было 20, а опрос отдавал 50 записей →
  журнал раздувался дублями. Расширено до 200.
* **QUIC-туннель на крошечных UDP-буферах** — главный кандидат на обрывы длинных
  ответов. Фикс: quick-туннель теперь на `--protocol http2` (TCP вместо UDP).
* **Повтор потока и кэш ответов** — обрывы переживаются клиентом (до 3 попыток,
  событие `retry` в чате), повторный вопрос идёт из кэша; ответ из кэша пишется
  в журнал диалога с меткой «из кэша», чтобы история его не стирала.
* **Диалоговая память оживлена** — реплики реально записываются (`remember_turn`),
  старые сжимаются в саммари, а в промт идут «свежие» факты (последние 12,
  а не первые).
* **Панель:** `Enter`/`Shift+Enter`, «ожидание» вместо «ждание», «Печать / PDF»,
  ошибка чата больше не пропадает; HTML панели читается по mtime — правки видны
  без рестарта процесса.

## 🗺️ Планы развития

Полная дорожная карта — `docs/ПЛАН_РАЗВИТИЯ.md`; ключевые пункты:

* **Надёжность:** именованный туннель (нужен домен в аккаунте Cloudflare),
  запасной транспорт (генерация в фоне + опрос `GET /chat/poll?rid=` — живые GET
  устойчивы), разбор «окон» на пути ПК→edge.
* **Режим «Разработка»:** классификатор типа задачи (bug/feature/refactor/…),
  план с альтернативами, обратный план, формальная проверка противоречий
  между шагами, иерархические планы и оценка сложности.
* **Память:** векторная память (SQLite + локальные эмбеддинги), дедупликация
  фактов со счётчиком подтверждений, память по проектам, забывание по
  приоритету и давности, экспорт/импорт памяти («поделиться памятью»).
* **Мультиагентность:** роли (планировщик/исполнитель/ревьюер), очередь сообщений,
  обмен файлами через `dev_sandbox`.
* **Наблюдаемость:** метрики Prometheus (`/metrics`) и Grafana-дашборд.
* **Безопасность:** ротация токена одной командой, rate limit в панели, аудит
  git-истории.
* **Обучение и калибровка:** few-shot на правках плана (diff), график калибровки
  `confidence` против реального исхода по записям рефлексии.

## 💡 Почему это интересно с инженерской точки зрения

* **Гибридная архитектура:** тяжёлые вычисления — в облаке, лёгкий клиент — на ПК.
  Это снижает порог входа и стоимость.
* **Честность в интерфейсе:** панель не приукрашивает — если это заглушка, она так
  и пишет; если токены оценены, а не точны — помечает это.
* **Глубокая проработка отказоустойчивости:** fallback, диагностика потоков,
  runbook — я не просто написал код, а документировал каждую проблему и её решение.
* **Проектонезависимость:** субагент можно подключить к любому проекту — игре,
  сайту, скриптам. Он работает с тем контекстом, который ему передали.
* **Активная разработка:** за последний день — несколько коммитов с фиксами
  dev-вкладки, потоков и панели. Проект живой и развивается.

## 1. Как это устроено

```
┌── ПК (только stdlib) ──────────────┐        ┌── Google Colab (бесплатно) ───────────┐
│ tools/thinking_cli.py  — команды   │  HTTP  │ llama_cpp.server  (LLM Qwen2.5-7B Q4) │
│ tools/thinking_panel.html — веб-   │ ─────► │ thinking_server.py (FastAPI:          │
│   панель: отчёты, диалог, мысли,   │  SSE   │  /plan /reflect /events …)            │
│ thinking/client.py     — клиент    │ ◄───── │ cloudflared  (публичный туннель)      │
│ thinking/fallback.py   — заглушка  │        └────────────────────────────────────────┘
└────────────────────────────────────┘
```

Принципы (закреплены в `docs/TZ_thinking_subagent.md`):

1. **Субагент только советует.** У него нет инструментов, нет доступа к файлам и
   к API изображений. Он возвращает JSON-план/совет, а выполняет — главный агент.
2. **Не блокирует работу.** Колбэки, таймауты и заглушка `thinking/fallback.py`:
   если Colab упал, вызов возвращается с `fallback=True`, работа продолжается.
3. **Всё пишется на диск.** События — `logs/thinking/thoughts.jsonl`,
   история диалога — `interactions.jsonl`, отчёты — `reports.jsonl`. Поэтому
   отчёты видны в панели, даже если их сделал другой процесс/сессия.
4. **Живой поток.** Мысли и шаги стримятся по SSE (`/events/stream`) и
   мгновенно появляются в панели.
5. **Честная выгода.** Панель считает KPI и прямо говорит, когда ускорение
   реально, а когда нет (см. §7).

## 4. Как поднять Colab: пошагово

### ⚡ Коротко

1. Открыть <https://colab.research.google.com> **в своём обычном браузере** (там,
   где вы залогинены в Google) и загрузить `colab/thinking_agent_ver3.ipynb`.
2. **Runtime → Run all** (ячейки A → C → D).
3. В **ячейке 2 (A)** по умолчанию `PROFILE = "dev"` — рекомендуемый профиль:
   качает **3B + 1.5B + 7B (≈7 ГБ)**, активна 3B — она и отвечает живьём на
   бесплатном Colab (≈2,5 ток/с). 7B нужна только для переключения во
   вкладке «Модели». `strong` (14B) даёт 0,05 ток/с, а `big` (30B, 17 ГБ)
   на бесплатном Colab не поднялась.
4. Выполнить **ячейку 7/7** — напечатает готовый адрес туннеля и готовую команду
   для ПК. Искать адрес в выводе ячейки D больше не нужно.

> **Почему «в своём браузере».** В браузере код-агента вход в Google-аккаунт
> блокируется («Couldn’t sign you in — браузер не поддерживает JavaScript»): это
> защита Google от автоматизированных браузеров, обойти её нельзя. Вводить пароль
> от аккаунта в автоматизированный браузер не нужно и не стоит.

**Как передать результат агенту.** Скопируйте из вывода ячейки 7/7 строку
`АДРЕС ТУННЕЛЯ` и токен и вставьте в чат — агент настроит ПК и прогонит полный
тест субагента. Либо вставьте вывод ячейки D (там `THINKING_URL=` и
`THINKING_TOKEN=`) — этого достаточно.

### Подробно

Одна команда на ПК собирает zip с исходниками, заливает его и генерирует готовый
ноутбук:

```bash
python scripts/build_colab.py --name thinking_agent_ver3.ipynb --ver ver3
```

**Личный ноутбук (рекомендуется).** Обычный ноутбук генерирует на Colab
**новый токен при каждом запуске**, поэтому после перезапуска Colab связь
падает с 401, пока токен не перенесён вручную. Личный ноутбук решает это
раз и навсегда — токен фиксируется внутри:

```bash
python scripts/build_colab.py --personal
```

Команда берёт токен из `config/thinking.local.json` (создаёт, если его нет) и
пишет `colab/thinking_agent_personal.ipynb`. **Этот файл в git не попадает**
(в `.gitignore`): внутри токен доступа. Обычный ноутбук из репозитория
токена не содержит вовсе — это проверяет тест.

С личным ноутбуком после перезапуска Colab меняется только адрес туннеля,
а на ПК достаточно одной команды без токена:

```bash
python tools/thinking_cli.py set-url "https://…trycloudflare.com"   # токен подставится сам
```

Дальше в браузере:

1. Открыть <https://colab.research.google.com> → **Upload notebook** → выбрать
   `colab/thinking_agent_ver3.ipynb`.
2. Подключить GPU: **Runtime → Change runtime type → T4 GPU** (для CPU-сборки
   сойдёт и без GPU, но ответы будут дольше).
3. **Runtime → Run all** (или запускать ячейки по очереди):
   | Ячейка | Что делает | Ожидаемый итог |
   |---|---|---|
   | 1 | скачивает zip исходников в `/content/tc` | `OK: исходники на месте` |
   | 2 (A) | зависимости, сборка llama-cpp (CPU/CUDA) и модели по профилю из строки `PROFILE` в её коде | `профиль моделей: …`, `OK-A` |
   | 3 (C) | собирает `/content/thinking_server.py` | `записан … строк: N` |
   | 4 (D) | поднимает LLM, API, cloudflared; смоук-тест | `смоук: X.X с`, `THINKING_URL=…`, `THINKING_TOKEN=…` |
   | 5 (E) | фон/снапшот (необязательно) | `фон запущен: снапшот событий каждые 60 с` |
   | 7 | печатает адрес туннеля и готовые команды | `АДРЕС ТУННЕЛЯ: https://…` |
4. Выполнить ячейку **7/7** — она напечатает адрес и готовую команду; на ПК:

```bash
python tools/thinking_cli.py set-url <THINKING_URL> <THINKING_TOKEN>
python tools/thinking_cli.py doctor
```

**Важно:**

* ссылка tmpfiles живёт ~60 минут. Если ячейка 1 упала со «ссылка истекла» —
  заново выполните `python scripts/build_colab.py`, вставьте новую ссылку в
  первую ячейку (или загрузите свежий `thinking_colab.ipynb`) и запустите её;
* то, что уже скачано (модель, окружение), при повторном запуске тех же ячеек
  переиспользуется — идемпотентность заложена;
* остановить всё: ячейка F (`cell_f_stop.py`) или `pkill -f 'llama_cpp|uvicorn thinking_server|cloudflared'`;
* если Colab закрылся/переподключился — URL туннеля обычно остаётся тем же,
  иначе перезапустите ячейку D и снова сделайте `set-url`.

## 5. Команды CLI и коды выхода

| Команда | Назначение |
|---|---|
| `doctor` | проверка связи, модели, токена, панели |
| `set-url <URL> [TOKEN]` | записать адрес/токен в `config/thinking.local.json` |
| `set-url --back` | вернуть предыдущую пару «адрес + токен» (заглушка ↔ Colab) |
| `url` | показать сохранённый адрес (токен маскируется) |
| `plan "задача" [--files a,b] [--constraint …] [--context …] [--max-steps N] [--stream] [--json]` | декомпозиция задачи → отчёт с шагами |
| `ask "вопрос" […]` | короткий совет (по умолчанию до 5 шагов) |
| `ask-multi "вопрос"` | один вопрос нескольким моделям параллельно |
| `reflect PLAN_ID --step N --result "…" [--observation …] [--error …] [--async]` | рефлексия после шага |
| `reflect-metrics` | пересчёт KPI «выгоды» по журналу |
| `models` / `use-model <путь>` | список моделей / переключение на лету |
| `dump [llm.log]` | скачать серверный файл (логи, дампы) |
| `tail [--n N] [--follow]` | журнал событий (живой поток) |
| `metrics` | KPI: обращения, планы, шаги, время ответа, заглушка |
| `panel [--port N]` | веб-панель (по умолчанию 127.0.0.1:8765) |

Коды выхода (полезно в скриптах и для агента):

| Код | Значение |
|---|---|
| 0 | успех |
| 1 | общая ошибка: ни одна модель не ответила / запрос не прошёл |
| 2 | Colab недоступен → ответ из заглушки (`fallback=True`) |
| 3 | нарушен контракт (валидация JSON-схемы) |
| 4 | сервер недоступен / ошибка соединения |
| 5 | отклонён токен (401/403) |
| 130 | прервано пользователем |

Любая команда принимает `--url <адрес>` (и `--token`): адрес действует только
на этот запуск и `config/thinking.local.json` не меняется.

### Локальная заглушка: разработка без Colab

`tools/mock_llm.py` отвечает на те же маршруты и в том же формате, что
ячейка C на Colab, но текст собирает из шаблона — поэтому панель, клиент и
CLI гоняются за секунды, без туннеля и без GPU.

```bash
python tools/mock_llm.py --port 8010                       # терминал 1
python tools/thinking_cli.py set-url http://127.0.0.1:8010  # терминал 2
python tools/thinking_cli.py doctor                        # HEALTH: ok, MODEL: mock-llm
python tools/thinking_cli.py set-url --back                # вернуться на Colab
```

Режимы `--mode` (или метка прямо в тексте запроса — на один вызов):
`slow` — первый токен через N секунд с пингами SSE, `error` — 503,
`drop` — поток рвётся посередине, `badjson` — мусор вместо JSON. Они нужны,
чтобы обрывы туннеля, откат и keep-alive проверялись **по заказу**, а не ждали,
пока бесплатный туннель сам порвёт соединение. Подробности и честные границы:
`docs/БЫСТРЫЙ_СТАРТ.md` §9.

Панель перезапускать после `set-url` не нужно — она перечитывает конфиг на
каждом запросе. Память, отчёты и таймлайн лежат на ПК, поэтому при
переключении меняется только то, кто печатает ответ.

## 6. Веб-панель (`python tools/thinking_cli.py panel`)

Адрес: <http://127.0.0.1:8765> — одна страница `tools/thinking_panel.html`,
всё на русском, тексты событий вставляются безопасно (`textContent`).

* **Отчёты** — цель, обоснование, шаги с ожидаемыми результатами, критерии,
  противоречия; при `fallback` — явная пометка «заглушка». Кнопка
  «Печать / PDF» — сохранение отчёта через диалог печати браузера.
* **Чат с субагентом** — живой диалог человека с нейросетью на Colab
  (`Enter` — отправить, `Shift+Enter` — новая строка). Ответ помечен: точное время,
  токены, использовалась ли память, не заглушка ли это; повторный тот же вопрос
  в течение 30 минут (`answer_cache_ttl`) отдаётся из кэша мгновенно — без
  нагрузки на Colab. Если Colab недоступен — честный ответ
  «субагент недоступен», работа не ломается.
* **Диалог** — хронология: что запросили, сколько ждали, что получили
  (склеивается из памяти процесса и `interactions.jsonl`, поэтому видны вызовы
  из любой сессии).
* **Токены** — сколько токенов ушло на промт и на ответы: полоса, график по
  вызовам и таблица. Точные цифры берутся из `usage` сервера; если сервер его не
  отдал — считаем по длине текста и **честно помечаем это как оценку**.
* **Связь агентов** — поток событий `thoughts.jsonl` в реальном времени (SSE).
* **Выгода и ускорение** — KPI и честные пояснения (см. §7).
* **Журнал** — сырой `thoughts.jsonl`.
* Кнопка **«Скачать отчёт .md»** выгружает диалог и отчёты в Markdown.

### Удаление отчётов и диалогов

У каждого отчёта и каждой записи диалога есть кнопка **«удалить»**, плюс
массовые действия над разделом: *все отчёты*, *старше суток*, *только
заглушки*, *весь диалог*, *очистить чат*. Удаление переписывает
`logs/thinking/*.jsonl` — это необратимо, поэтому спрашивает подтверждение.

### Память субагента

`logs/thinking/memory.json` — то, что субагент помнит между сессиями:

| Поле | Смысл |
|---|---|
| `profile` | одна строка о проекте |
| `facts` | факты, добавленные вручную или кнопкой «Запомнить» в панели |
| `turns` | последние 12 реплик чата (что спросили — что ответили) |

В промт уходит только срез: до 12 фактов и до 6 последних реплик, обрезанных по
300 символов. Файл можно править руками — он обычный JSON. Кнопка
«Стереть память» и крестик на факте удаляют точечно.

Панель не требует Colab: при пустом URL она честно пишет «НЕТ СВЯЗИ · base_url
пуст — выполните set-url» и продолжает показывать накопленную историю.

Панель не стартует на занятом порту: если `8765` уже держит другой процесс
(на Windows `SO_REUSEADDR` раньше позволял молча сесть поверх), выводится
подсказка и код выхода `4` — запустите `panel --port 8766`.
События панель получает двумя путями: SSE-потоком и фоновым опросом
`GET /events` каждые `panel_poll` секунд (по ТЗ опрос — основной канал),
поэтому «Связь агентов» не зависят от того, дошли ли ping-строки через туннель.

## 7. Как агенту активно работать с субагентом

Сценарии вызова:

| Ситуация | Команда | Зачем |
|---|---|---|
| Пришла новая нетривиальная задача | `plan "…" --files … --stream` | разбить на шаги, получить критерии и список противоречий до начала работы |
| Нужен быстрый совет/второе мнение | `ask "…"` | короткий ответ без большого плана |
| Шаг выполнен (успех) | `reflect ID --step N --result "…"` | обновить план, получить следующие шаги |
| Шаг провалился | `reflect ID --step N --result "…" --error "…"` | скорректировать курс (`status: adjust/abort`) |
| Нужно не блокироваться | `… --async` | рефлексия уходит в фон, работа продолжается |
| Хочется видеть ход мыслей | `tail --follow` или вкладка «Связь агентов» | стрим идёт из Colab по SSE |
| Второе мнение по спорному вопросу | `POST /api/chat` живой панели | диалог с памятью проекта, повторный тот же вопрос — мгновенно из кэша |

**Модель по нужде.** Для глубоких вопросов включается более сильная модель:
`python tools/thinking_cli.py use-model 7b|3b` (20–60 с) либо вкладкой
«Модели» в панели. На CPU: 7B ≈ 1.3 ток/с (ответы 2–4 минуты), 3B ≈ 2.5 ток/с.

**Живые пробы (03.10).** Агент реально пользовался субагентом в своей работе:

| Зачем | Модель | Шло | Что получено |
|---|---|---|---|
| Критика теории обрывов + приоритет бэклога | 3B | 76.8 с, 184 токена | второе мнение: keep-alive сервером первым — совпало с независимым выводом |
| Дизайн сотрудничества «агент ↔ субагент» | 7B | 124.8 с, 111 токенов | тезисы: что делегировать, что оставить себе, как проверять пользу |

**Механизм против шума.** Решения принимает агент; субагент — второе мнение
по спорным вопросам (диагностика, приоритеты, дизайн). Довод считается
значимым, если проверяется фактами задним числом: журнал обращений, замеры,
тесты. Пример — моя теория «первый токен позже stall» подтверждена журналом
20:12 (ошибка) / 20:43 (успех с фолбэком).

Рекомендации:

* Передавайте осмысленный контекст: `--files` — реально существующие пути,
  `--constraint` — жёсткие ограничения, `--context` — что уже известно.
  Субагент не читает файлы сам и **не выдумывает пути**: неизвестное он вернёт
  в `unknown_files` — это сигнал вам уточнить.
* Используйте `contradictions` из ответа как чек-лист рисков, а
  `success_criteria` — как условия «задача сделана».
* Субагент отвечает по-русски; латиница в ответе допустима только в тегах
  `action` (`build test refactor verify docs prompt debug release`).
* Параллельность безопасна: вызовы независимы, история склеивается по
  `at+kind+request`, так что два процесса не затирают отчёты друг друга.

**Честная выгода.** Реально ускорение даёт:

* план и рефлексия идут **параллельно** вашей работе (фоном), а не вместо неё;
* агент не тратит попытки вслепую — меньше циклов «сделал → сломал → переделал»;
* при падении Colab есть заглушка — простой не наступает вообще.

Чего ждать не стоит: сам LLM на CPU отвечает десятки секунд (до `plan_timeout`),
поэтому «ускорение» — это качество и структура решений, а не мгновенные ответы.
Панель показывает метрики (`среднее время ответа`, `срабатывания заглушки`),
чтобы вы видели реальную цифру, а не обещания.

## 8. HTTP API (для прямых вызовов)

Базовый URL — из туннеля Colab. Заголовок `X-Agent-Token: <токен>` (или
`?token=`), `/health` без токена недоступен.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | живость + версия |
| GET | `/metrics` | счётчики сервера |
| GET | `/events?since=&tail=` | журнал событий (JSON) |
| GET | `/events/stream` | SSE — живой поток мыслей |
| POST | `/plan` | план по схеме (`PlanRequest` → `PlanResponse`) |
| POST | `/plan/stream` | то же с потоком текста (NDJSON/SSE) |
| POST | `/reflect` | рефлексия шага (`ReflectRequest`) |
| POST | `/cancel/{plan_id}` | отмена длинного запроса |

Пример:

```bash
curl -s -X POST "$THINKING_URL/plan" -H "X-Agent-Token: $THINKING_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"task":"Разбить отчёт на шаги","context":{"files":["a.py"]},"max_steps":6}'
```

Схемы и правила валидации — `thinking/schemas.py`, снимок — `docs/schema_plan.json`.

## 9. Память и история

| Файл | Что хранит |
|---|---|
| `logs/thinking/thoughts.jsonl` | события: мысли, шаги, ошибки (вкладка «Журнал», «Связь агентов») |

## 10. Настройки

`config/thinking.json` (без секретов):

| Поле | Смысл | По умолчанию |
|---|---|---|
| `enabled` | включать ли субагента | `true` |
| `base_url` | адрес Colab (обычно пуст — лежит в local/env) | `""` |
| `timeout` / `connect_timeout` | общий и на соединение | 45 / 5 с |
| `stream_timeout` | read-timeout SSE-потока (должен быть **больше** ping-интервала сервера) | 40 с |
| `panel_poll` | как часто панель опрашивает `GET /events` (первичный канал по ТЗ) | 5 с |
| `retry` | 3 попытки, экспоненциальная пауза | — |
| `stream` | стримить ли мысли по SSE | `true` |
| `fallback_on_error` | отдавать заглушку при недоступном Colab | `true` |
| `plan_timeout` / `reflect_timeout` | лимиты ответа LLM (на CPU план живёт минуты) | 360 / 180 с |
| `stream_stall` | сколько ждать следующего байта потока, **после первого события** (должен быть **больше** ping-интервала сервера) | 45 с |
| `stream_stall_first` | сколько ждать **первый** байт потока: на CPU модель думает минутами (живой замер 05.10 — 86 с до первого токена плана), и общий `stream_stall` рвал ещё не начавшийся поток | 180 с |
| `stream_retries` | повторы обрыва SSE | 2 |
| `job_first` | пробовать ли сначала асинхронное задание (`/plan/async` + опрос `/job/{id}`). Основной маршрут плана и рефлексии: ответ приходит сразу, поэтому лимит прокси (120 с на длину ответа) не мешает длинной генерации | `true` |
| `job_poll` | как часто опрашивать готовость задания | 6 с |
| `stream_first` | пробовать ли поток, если задание недоступно. `false` — сразу обычный не-потоковый маршрут | `true` |
| `stream_first_streak` | после скольких обрывов потока подряд перестать его пробовать | 2 |
| `stream_first_pause` | на сколько секунд после этого тихий период | 600 с |
| `state_path` | файл состояния тихого периода (`logs/thinking/state.json`). Нужен потому, что CLI — отдельный процесс на каждый вызов: без файла счётчик обрывов обнулялся бы при каждом запуске | `logs/thinking/state.json` |
| `chat_json_timeout` | лимит не-потокового `/chat` | 300 с |
| `chat_timeout` / `dev_timeout` | лимиты потоков чата и режима разработки | 600 / 600 с |
| `breaker_pause` | пауза предохранителя после 5 ошибок подряд | 600 с |
| `answer_cache_ttl` | кэш ответов панели | 1800 с |
| `panel_host` / `panel_port` | адрес панели | 127.0.0.1:8765 |
| `log_path` / `interactions_path` / `reports_path` | куда пишется история | `logs/thinking/*` |

Секреты: `config/thinking.local.json` либо переменные окружения
`THINKING_URL` и `THINKING_TOKEN`. Приоритет у локального файла: он →
`config/thinking.json` → переменные окружения (`client.py: reload_config`).

> ⚠️ **Никогда не коммитьте `config/thinking.local.json`** — там адрес и токен
> доступа к Colab. Файл внесён в `.gitignore`, шаблон без секретов —
> `config/thinking.local.json.example`. Если токен всё же утёк в публичный
> репозиторий — перезапустите ячейку D в Colab (токен сгенерируется новый)
> и сделайте `set-url` заново.

## 11. Отказоустойчивость: что делать, если что-то не так

| Симптом | Причина | Действие |
|---|---|---|
| «НЕТ СВЯЗИ · base_url пуст — выполните set-url» | не задан адрес | `set-url <URL> <TOKEN>` |
| `exit 4`, сервер недоступен | Colab уснул/закрылся, туннель умер | открыть ноутбук → ячейка D → новый `set-url` |
| `exit 2`, «заглушка» | Colab недоступен, но работа продолжена | не блокируйтесь; позже повторите вызов |
| `exit 3`, «контракт нарушен» | LLM вернул мусор вместо JSON | повторите вызов; при частоте — снизить `max_tokens`/перейти на 3B |
| `exit 5` | неверный токен | перескопировать `THINKING_TOKEN` из ячейки D |
| ответы очень медленные | CPU-инференс 7B | `plan_timeout` поднять, либо модель Qwen2.5-**3B** (быстрее в ~2 раза) |
| ячейка A упала на `--ctx_size` / `--model_name` | версия llama-cpp принимает `--n_ctx` / `--model_alias` | см. `cell_d_launch.py` — используются новые флаги |
| «ссылка истекла» в ячейке 1 | прошло >60 минут с `build_colab.py` | перезапустить `build_colab.py` и обновить ссылку |
| панель показывает старые отчёты | jsonl общий — это норма | история читается с диска, чистка в §9 |
| поток ответа обрывается: «Жду…» вечно, done не приходит | обрыв SSE на стороне туннеля | `docs/ДИАГНОСТИКА_ПОТОКОВ.md` — хронология проб, матрица решений, runbook |
| нужен свежий ноутбук | — | `python scripts/build_colab.py` → Upload notebook |

Логи на Colab: `/content/llm.log` (LLM), `/content/thinking_api.log` (API),
`/content/tunnel.log` (туннель), `/content/launch.log` (ячейка D).
`GET /dump/tunnel.log` с заголовком `X-Agent-Token` отдаёт лог туннеля на ПК.

связь и бюджет latency, отклонение чужого токена (401), метрики и события,

прошло, `1` — есть провалы, `2` — сервер недоступен/URL не задан.

`docs/plan_work_first.md`.

## 13. Использование в другом проекте

Субагент проектонезависим. Чтобы подключить его к новой задаче:

1. Скопируйте каталог `ThinkingAgent` (или добавьте его в `PYTHONPATH` проекта).
2. В коде проекта:

```python
from thinking.client import ThinkingClient

c = ThinkingClient()
plan = c.plan_with_fallback(
    task="Сделать X",
    context={"files": ["src/x.py"], "cwd": "."},
    constraints=["не ломать API"],
    on_event=lambda e: print(e["type"], e["text"]),   # живые мысли
)
print(plan["steps"])                                  # шаги с expected_output
```

3. `plan_with_fallback` **не бросает исключение** при недоступном Colab —
   вернёт заглушку с `fallback=True` (если в конфиге включён fallback).
4. Всё остальное (панель, история, KPI) работает как обычно — см. §3–§7.

Готовые рецепты интеграции и answers на частые вопросы — в
`docs/TZ_thinking_subagent.md`.

## 14. Репозиторий Git и GitHub

Проект живёт в GitHub: **<https://github.com/petrles444-source/agent>**
(ветка `main`, содержимое — этот каталог целиком).

**Что НИКОГДА не попадает в git** (закреплено в `.gitignore`):

| Что | Почему |
|---|---|
| `config/thinking.local.json` | секреты: адрес и токен Colab (шаблон — `...example`) |
| `logs/` | локальная история: переписка, события, отчёты (6+ МБ) |
| `__pycache__/`, `*.pyc` | артефакты Python |
| `dumps/`, `colab_downloads/`, `dev_sandbox/`, `_thinking_colab.zip` | рабочие артефакты: дампы, логи Colab, песочница разработки, сборка ноутбука |

**Как обновляется репозиторий.** После каждой значимой порции изменений
(правки кода, документации, ноутбука) выполняется:

```bash
git add -A
git commit -m "что изменилось"
git push
```

Команды выполняются из каталога `ThinkingAgent` — git сам найдёт репозиторий.
Репозиторий намеренно ограничен этим каталогом: другие проекты из
`WelcomeScreen/` в git не отслеживаются и в GitHub не попадают.

**Если push просит логин/пароль** — GitHub больше не принимает обычные
пароли: либо один раз включите Git Credential Manager
(`git config --global credential.helper manager`) и при первом push
завершите авторизацию в открывшемся браузере, либо создайте Personal Access
Token (GitHub → Settings → Developer settings → Tokens) и используйте его
как пароль.
