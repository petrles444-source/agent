# Код-аудит `thinking/client.py` (~1925 строк)

## Оценка файла

Транспортная архитектура сделана сильно: ретраи разведены между `_open` (соединение/HTTP) и `_stream_read` (обрывы SSE), предохранители разделены по каналам (AUD-05), учёт планов собран в одном `_account_plan` (AUD-06), секреты проверяются на всех точках входа, токен в `status()` больше не течёт (B-8). Однако «честный учёт» остаётся дырявым в трёх местах: провалы потокового плана не записываются вовсе, метрика «в фоне» не может стать ненулевой ни при каких условиях, а три ветки ошибок чата считают по-разному. Состояние предохранителя и живого потока не переживает смену адреса — сценарий «Colab умер → set-url на новый» блокируется до 10 минут чужими ошибками. Ещё две реальные поломки лежат на стыке с панелью: кнопка удаления отчётов-заглушек молча ничего не удаляет, а `clearAll/clearOld` воскрешает записи из in-memory буфера.

## Находки

### [A] Критично (падение/утечка/безопасность)

- **[A] thinking/client.py:389–396 — `_json` не оборачивает чтение тела ответа.** `with self._open(...) as resp: raw = resp.read()` стоит вне `try`: `socket.timeout`, `http.client.IncompleteRead` (не наследует OSError!), `ConnectionResetError` вылетают из `_json` **сырыми**, не став `last_error`/предохранитель. `chat()` ловит только `ThinkingError` (стр. 1130), `models()`/`parallel_models()` — тоже, CLI-хендлер `/api/chat` (`tools/thinking_cli.py:1017`) — тоже → исключение уходит из `do_POST` без outer-try → `BaseHTTPRequestHandler` роняет соединение без ответа, фетч панели получает network error вместо JSON и офлайн-заглушка чата не срабатывает. Это основной обещанный контракт модуля («исключение только в `plan_with_fallback`») и типовой сценарий для этого проекта — обрыв тела посреди ответа на живом туннеле. **Фикс:** нормализовать ошибки чтения в `ThinkingError`:
  ```python
  def _json(...):
      try:
          with self._open(method, path, body, timeout) as resp:
              raw = resp.read().decode("utf-8", "replace")
      except ThinkingError:
          raise
      except (OSError, http.client.HTTPException) as exc:
          self.last_error = str(exc)[:200]
          raise ThinkingError(f"обрыв чтения ответа: {exc}") from exc
  ```

### [B] Важно (логика/устойчивость)

- **[B] thinking/client.py:1765–1768 ↔ tools/thinking_panel.html:982–987 — кнопка «удалить отчёты из заглушки» никогда ничего не удаляет.** Панель шлёт только `{kind:"report", n:n}` (без `at` и `rid`), а ветка удаления по номеру требует совпадения **и** `n`, **и** `at` (`str(line.at) == str(at)` → `"" == "<дата>"` → всегда False). `removed=0` молча, результат в `clearFallback` даже не читается. Заявленная функция неработоспособна, тесты её не видят (`check('"clearAll"' in ...)` — строковые). **Фикс:** в панели передавать `at: r.at` рядом с `n` (или в `delete_history` при пустом `at` удалять строго по `rid`, а не по одному `n`); добавить поведенческий тест на `n`+`at`.

- **[B] thinking/client.py:1780–1783 — `delete_history` без `rid` не чистит `self.interactions`/`self.reports` → «все отчёты/весь диалог/старше суток» воскрешают записи.** Фильтр памяти стоит только под `if rid:`; дальше `_disk_cache` сбрасывается, и `_load_history` (1804–1815) заново мержит in-memory список с очищенным диском — удалённые этим процессом записи вернутся в `status()`, «Выгоду» и «Токены» и исчезнут лишь после рестарта панели. Кнопки `clearAll`/`clearOld` панели (html:967–981) попадают ровно в эту ветку. **Фикс:** при `before`/«всё» тоже фильтровать память той же предикатной функцией:
  ```python
  if rid:      self.reports = [r for r in self.reports if r.get("rid") != rid]; ...
  elif before: self.reports = [r for r in self.reports if str(r.get("at","")) >= before]; ...
  elif n is None: self.reports = []; self.interactions = []
  ```

- **[B] thinking/client.py:461–503 — провал `plan_stream` не записывается ни в журнал, ни в метрики.** У `plan()` ошибка попадает в `stats["errors"]` + `_record(ok=False)` (433–437), у `plan_stream` исключение просто улетает наружу. При мёртвом туннеле `plan_with_fallback` идёт по ветке «транспорт мёртв → локальный шаблон» (700–706) и журналирует **только** `ok=True/fallback` — в «Диагностике/Ошибках» ноль ошибок при полном провале; `stream_error` из CLI (`_plan_streamed`) тоже ничем не закрепляется. **Фикс:** обернуть `_stream_read` в `try/except ThinkingError` в `plan_stream` с записью `self.stats["errors"] += 1; self._record("plan", task, t0, ok=False, ...)` перед пробросом — симметрично `plan()`.

- **[B] thinking/client.py:114–126, 700–706 — `_is_read_timeout` решает по подстроке в тексте ошибки и может принять живой сервер за мёртвый транспорт.** Текст `ThinkingError("сервер: LLM backend недоступен: ReadTimeout")` (cell_c_server.py:797 шлёт `type(exc).__name__`) содержит `"readtimeout"` → проверка истинна → `plan_with_fallback` пропускает не-потоковый `/plan` и сразу отдаёт шаблон, хотя сервер жив и ошибка была транзиентной; в лог пишется ложное «транспорт не отвечает». При этом `chat_stream` (1342) и `reflect` (550) корректно исключают префикс `"сервер:"` — обработка непоследовательна. **Фикс:** в `plan_with_fallback` сначала отсечь серверные ошибки, как делают соседи: `if str(stream_error).startswith("сервер:"): → попытка plan()`, и сузить `_is_read_timeout` до типов исключений/маркеров `_stream_read` («оборвался после»), а не произвольной подстроки.

- **[B] thinking/client.py:316–322, 266–286, 228–264, 288–303 — предохранители не сбрасываются при смене адреса.** Ни `set_url`, ни `reload_config`, ни `set_token` не трогают `_cb_open_until/_cb_stream_until/_cb_*_errors` (grep подтверждает: `_cb_` встречается только в `__init__` и `_open`). Сценарий спасения «Colab умер, 5 ошибок → предохранитель открыт → пользователь выполнил `set-url` на свежий туннель» — новый адрес блокируется до конца старой паузы (до 600 с) с сообщением «предохранитель: пауза ещё N с»; панель при этом уже ходит по новому URL. **Фикс:** в `reload_config()` при изменившихся `(base, token)` обнулять оба счётчика и обе паузы (адрес новый — старые ошибки к нему не относятся).

- **[B] thinking/client.py:316–322, 368–386 — после истечения паузы счётчик предохранителя не сбрасывается: достаточно 1 ошибки, чтобы открыть его снова.** Успех — единственное место сброса (341–342), но во время паузы REST-каналу успех недоступен (гейт блокирует), а если мёртв и поток — счётчик остаётся ≥5. После `gate` экспайра первый же неудачный вызов → `_cb_errors = 6 ≥ 5` → новая пауза 600 с, и так по кругу. Семантика «5 ошибок подряд» превращается в «1 ошибка раз в 10 минут», а лог «предохранитель открыт: 6 ошибок подряд» вводит в заблуждение. **Фикс:** при истечении паузы сбрасывать счётчик: `if time.time() >= gate and gate: self._cb_errors = self._cb_stream_errors = 0` в начале `_open`, либо открывать гейт только при `>= limit` и обнулении по таймеру.

- **[B] thinking/client.py:741–775 ↔ tools/thinking_cli.py:905–916 — смена URL не переподключает живой SSE: split-brain «REST новый / события старые».** `_stream_loop` читает `self.base` только при каждом новом коннекте, а соединение живёт вечно (сервер шлёт `: ping` каждые 10 с, cell_c:759–764 — read-timeout 40 с не срабатывает). После `set-url` панель получает события от **прежнего** сервера (например, переключение на заглушку, пока Colab ещё жив) и никогда не переключится сама; `_sync_target` только логирует новый адрес. **Фикс:** `reload_config()`, вернувший `True`, должен дёргать `self._stop.set()` + перезапуск потока (или хранить `_connected_base` и рвать соединение при расхождении с `self.base` в цикле чтения).

- **[B] thinking/client.py:489–492 + 1261–1262 — `plan_stream(remember=True)` пишет каждое token-событие в `thoughts.jsonl` и буфер.** Сервер отдаёт `{"type":"token","text":piece}` **без `seq`** (cell_c:815), поэтому дедуп в `_remember_ev` (828: `if seq and ...`) пропускает всё подряд: одна строка плана (сотни токенов) = сотни строк журнала и сотни `open/stat/append` посреди стрима (заметно на Windows), буфер этого процесса затирается под завязку. Остальные потоки (`chat/dev/reflect`) `remember` не передают — флоуд характерен только для плана. **Фикс:** в `_stream_read` не запоминать `etype == "token"` (`if remember and etype not in ("error", terminal, "token")`) — рацио/шаги и так попадают в буфер, а токены человек видит через `on_event`.

- **[B] thinking/client.py:891–910, 1652, 616–620, 1841–1848 — метрика «выполнено в фоне» никогда не может быть ненулевой.** Ни один вызов в проде не передаёт `background=True` (grep: только `_record`-дефолт и тест `thinking_test.py:213–226`, подставляющий запись в файл руками); `_record_chat` вообще хардкодит `False`, а `reflect --async` (CLI:318–339) после перехода на дочерний процесс тоже не помечает фон. Следствия: колонка «в фоне» в панели всегда «0.0 с», суммарное время async-рефлексий попадает в `blocked` как блокирующее, а правило в `reflect_metrics` `blocked_ms > max(60_000, 3 * max(background_ms, 1))` (616) сравнивается с единицей и срабатывает при любых >60 с. **Фикс:** пробросить флаг: `reflect(..., background=False)` → `_record(..., background=background)`, а в CLI `--async` передавать `--background` в дочерний процесс.

- **[B] thinking/client.py:1156–1174 + 1057–1065 — три разные семантики «ошибки» в чате.** (1) Модель промолчала → подставляется заглушка «Субагент промолчал…», `_record_chat` без `ok` → `ok=True`, `stats["errors"]` не растёт; (2) офлайн-ветка через `_chat_via_plan` (пустой `out`) при смерти Colab возвращает `local-fallback` **без** `stats["errors"] += 1`, в отличие от основной ветки (1137); (3) `_account_multi` при «ни одна модель не ответила» пишет `ok=False`, но тоже не трогает `stats["errors"]`. В итоге «ошибок» в `benefits()`/`notes` зависит от того, какой именно путь сработал, и занижается на два из трёх. **Фикс:** во всех трёх ветках перед возвратом/выходом делать `self.stats["errors"] += 1`, а для случая «промолчал» либо ставить явный `ok=False` в `_record_chat`, либо документировать, что это «успешный вызов без текста».

### [C] Мелочь (качество/надёжность)

- **[C] thinking/client.py:364–367 — `_open` спит после последней попытки.** `time.sleep(wait)` стоит в конце каждой итерации без проверки `i + 1 < attempts`: на каждом полном провале теряется ещё `backoff**attempts` (3.4 с по умолчанию, до 15 по cap), `health()` при офлайне занимает ~16 с вместо ~12. **Фикс:** `if i + 1 < attempts: time.sleep(wait)` (предупреждение логировать всегда).

- **[C] thinking/client.py:330–367 + 432, 1126–1129, 1430–1451 — нет общего дедлайна: `attempts × timeout`.** Каждая из 3 попыток получает полный таймаут (`plan_timeout` 360 → до ~18 мин на один `plan()` при чёрной дыре; `/chat` 300×3 ≈ 15 мин, `/dev` 600×3 = 30 мин) — вызывающая кнопка панели висит без ограничения. **Фикс:** считать абсолютный дедлайн `t_deadline = t0 + timeout` внутри `_open` и уменьшать `timeout` каждой следующей попытки.

- **[C] thinking/client.py:1240 — бюджет повторов `_stream_read` берёт `chat_timeout` для всех потоков.** `budget = max(stall*2, chat_timeout 600)` одинаков для `/plan/stream`, `/dev/stream`, `/reflect/stream`: `dev_timeout` (1430) и `reflect_timeout` (524) действуют только на не-потоковые маршруты, поток их игнорирует — при этом смешение не задокументировано (в отличие от осознанного комментария про `stream_stall` в 475–476). **Фикс:** передавать `budget=` параметром из каждого вызывающего (`plan_stream→chat_timeout`, `dev→dev_timeout`, `_reflect_stream→reflect_timeout`) либо переименовать в `stream_budget` и прокомментировать.

- **[C] thinking/client.py:730–736 — `start_stream()` в окне живости старого потока молча не запускает новый.** Порядок: сначала `if self._reader.is_alive(): return`, и только потом `_stop.clear()`. Если звать `stop_stream(); start_stream(cb)` быстрее, чем старый поток выйдет из блокирующего чтения (до 40 с), новый вызов вернётся **не сбросив** `_stop` → старый поток умрёт по флагу, новый не стартует — поток событий мёртв молча. Плюс повторный `start_stream(cb2)` при живом потоке тихо игнорирует новый колбэк. Текущие вызывающие (CLI:378, 903) такой последовательности не создают — это API-ловушка. **Фикс:** сохранять `_stop`-флаг и колбэк: если поток жив и запрошен другой `on_event` — ставить `_stop`, `join(timeout=read_to)` и стартовать новый; либо явно задокументировать «start_stream идемпотентен и колбэк не меняется».

- **[C] thinking/client.py:438–440, 563–570 — не-словарный ответ `/plan` и `/reflect` проходит без учёта и без валидации.** Если сервер вернул список/строку (JSON валиден, `json.loads` прошёл), `if isinstance(out, dict)` просто пропускает учёт, и сырой объект уезжает вызывающему: `plan_with_fallback` отдаёт его как «план», дальше `plan.get(...)` → `AttributeError` в CLI/панели; `reflect_metrics` падает на `out.get("status")`. **Фикс:** `if not isinstance(out, dict): raise ThinkingError(f"сервер вернул не словарь: {type(out).__name__}")` — симметрично `set_model` (1203–1204).

- **[C] thinking/client.py:717–724 — фолбэк-запись `plan_with_fallback` теряет `author`.** `stream_kw` автора фильтрует и пробрасывает (682–683), успешные пути учтывают `author`, но `_record(..., fallback=True)` на строке 720 вызывается без `author=` → человек, задавший задачу через панель, в «Ленте обращений» увидит «агент» (неполнота фикса B-2). **Фикс:** `author=kw.get("author", "agent")` в этот вызов (и добавить параметр `author` в `local_plan`-ветку теста).

- **[C] thinking/client.py:7–9 vs 1018–1032 — докстринг модуля врёт.** «Единственное место, где бросается исключение, — `plan_with_fallback`» не соответствует коду: `multi_chat` (1032), `chat_stream` на `"сервер:"` (1343), `dev` (1443), `reflect` (562), `plan` бросают осознанно. **Фикс:** переформулировать: «исключения — контракт (`SchemaError`) и транспорт (`ThinkingError`); мягкую деградацию дают `plan_with_fallback` и `chat`».

- **[C] thinking/client.py:857–866 — `iter_thoughts` — мёртвый код с логикой голодания.** Метод нигде не вызывается (grep: только определение и ТЗ), а если бы вызывался: после заполнения буфера `seen = len(self._events) == 500`, обрезка `del self._events[:-500]` (833–834) держит длину ровно 500, и срез `self._events[500:]` **навсегда пуст** — итератор перестаёт отдавать новые события. **Фикс:** удалить вместе с упоминанием в ТЗ либо переписать на индекс по `seq` (`self._events[i]` с учётом обрезки) и покрыть тестом.

- **[C] thinking/client.py:209, 1079, 1154, 1178, 1375 — `token_stats` записывается, но никогда не читается.** Ни `status()`, ни `benefits()`, ни `tokens()`, ни CLI его не используют — вся работа `TokenLedger` (включая ветку «оценка/точно») никому не отдаётся, при этом токены дублируются в `_record_chat`/журнал. **Фикс:** либо отдать `token_stats.as_dict()` в `status()` (как показ точных цифр процесса рядом с журнальными), либо удалить и оставить журнал как единственный источник.

- **[C] tools/thinking_cli.py:381–397 + thinking/client.py:748–775 — `tail --follow` никогда не показывает «нет связи».** В цикле проверяется `client.online`, но за его изменение отвечает только REST (`sync_history` зовётся один раз до цикла), а SSE-ветка `online` не трогает намеренно (769–770): после стартового успеха флаг залипает в `True` (предупреждение недостижимо), после стартового провала — в `False` (спам каждые 15 с независимо от реального состояния потока). **Фикс:** в `cmd_tail` периодически (раз в 15 с) дёргать `client.health(timeout=3)` либо выводить `client.stream_ok` вместо `online`.

- **[C] thinking/client.py:401–403 — `health(timeout=…)` молча обрезается до `connect_timeout`.** `min(timeout, self.connect_timeout or timeout)` при дефолтных 5 с: прогрев `health(timeout=15)` в панели (CLI:935) реально ждёт максимум 5 с — параметр вызывающего бесполезен, а расхождение не задокументировано. **Фикс:** `min(timeout, self.connect_timeout)` только для внутренних быстрых проверок, либо переименовать/прокомментировать, что это потолок именно для health.

### [D] Стиль/читаемость

- **[D] thinking/client.py:743–745 и config/thinking.json:25 — устаревшее число в комментарии: «интервал ping сервера (25 с)».** Фактически `/events/stream` пингует каждые **10 с** (cell_c:759–764), а `with_heartbeat` — каждые **15 с** (cell_c:476); «25» не встречается нигде. Требование «read-timeout > ping» сейчас выполняется (40 > 15), но при правке конфига по этому тексту можно зря поменять `stream_timeout`. **Фикс:** привести оба места к «10 с для /events/stream, 15 с для потоковых маршрутов».

- **[D] thinking/client.py:918–920 — событие `interaction` пишется с `seq = int(time.time()*1000)` мимо `_lock`/`_seq_local`.** Локальная коллизия seq, починенная в `_remember_json` (C-2), здесь не закрыта: два `_record` в одну мс дадут одинаковый seq, и если такую строку когда-нибудь повторно прочитают через `_remember_ev`, вторая потеряется. **Фикс:** вынести `max(int(time.time()*1000), self._seq_local + 1)` под `self._lock` в хелпер `_next_seq()` и использовать в обоих местах.

- **[D] thinking/client.py:254–264 — `set_url` не валидирует схему.** `base_url` записывается как есть; urllib примет и `file://…`, и `ftp://`, а на GET-маршрутах (`/health`, `/events`) попытается прочитать локальный файл как «ответ сервера». Риск минимален (команда локальная, панель set-url не вызывает), но защита дешёвая. **Фикс:** `if base and not base.startswith(("http://", "https://")): raise ThinkingError("адрес должен начинаться с http(s)://")`.
