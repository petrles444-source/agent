## 1. Резюме и оценки

ThinkingAgent — подсистема «субагент-советник»: LLM (Qwen2.5 1.5B/3B/7B) крутится в бесплатном Google Colab на llama.cpp, наружу выставлена через быстрый туннель Cloudflare, а на ПК живёт синхронный клиент на чистой stdlib, CLI и веб-панель на 9 вкладок. Проект написан аккуратно, с редкой для хобби-проекта культурой: атомарная запись файлов, дедупликация событий, предохранитель транспорта, кэш ответов, откаты файлов, честная пометка «оценка» у неточных цифр токенов, диагностика обрывов SSE с хронологией улик и CI на двух ОС.

| Категория | Оценка | Комментарий |
|---|---|---|
| Архитектура и дизайн | **8/10** | Чистое разделение контракт/клиент/сервер/панель; stdlib-дисциплина; есть дублирование клиент↔сервер |
| Качество кода | **7/10** | Читаемый, комментированный; есть мёртвый код, mutable class-атрибут, опечатки в маршрутах |
| Отказоустойчивость | **8/10** | Многоуровневые фолбэки; но предохранитель связывает SSE и REST, сторож не лечит «зависший» процесс |
| Тестирование | **5,5/10** | 325 проверок зелёные, но большинство — «строка есть в файле»; JS панели и FastAPI-сервер не тестируются поведенчески; есть нарушение изоляции тестов |
| Безопасность | **6/10** | Токен есть, редьюсер секретов есть; но токен в query-string, CORS `*`, нет проверки Host у панели, режим Dev не проверяет код на секреты |
| Документация | **9/10** | README на 15 разделов, диагностика, ТЗ, план развития; расхождения мелкие |
| Наблюдаемость | **8/10** | Журналы, метрики, рефлексия по метрикам; дыры в учёте (plan_stream, стриминговые ответы) |
| Производительность | **6/10** | CPU-инференс 1–3 ток/с — объективное ограничение; клиент оптимизирован (кэш по mtime, TTL-кэш ответов) |
| **Итого** | **7,3/10** | Зрелый пет-проект инженерного уровня выше среднего; главные риски — в непротестированной связке «панель JS ↔ CLI-хендлеры» и в честности метрик |

**Главный вывод:** кодовая база здорова, но три функциональных бага подтверждены прямо сейчас (экспорт/импорт памяти падает с `NameError`; кнопка «Применить» в режиме «Разработка» применяет не тот код; `reflect --async` теряет результат), и все три выжили именно потому, что тесты проверяют наличие строк в файлах, а не поведение. Ниже — полный реестр с точными координатами.

## 3. Карта системы (как есть)

```
ПК (Windows, Python 3.12/3.14, только stdlib)
├── thinking/client.py     — синхронный клиент: REST + SSE, память, журналы, метрики
├── thinking/schemas.py    — контракты Plan/Reflect/Chat + extract_json + redact_secrets
├── thinking/fallback.py   — офлайн-заглушка local_plan
├── tools/thinking_cli.py  — CLI (plan/ask/reflect/tail/panel/…) + локальный HTTP-сервер панели
│                            (ThreadingHTTPServer, 127.0.0.1:8765) + кэш ответов
├── tools/thinking_panel.html — SPA-панель: 9 вкладок, SSE /events, стрим /api/chat/stream
├── tools/thinking_test.py — офлайн-проверки (CI), thinking_online_test.py — живой прогон
└── logs/thinking/*.jsonl  — мысли/взаимодействия/отчёты/чат/память (в git не попадают)

Colab (ячейки A/C/D/E/F)
├── A: установка llama-cpp-python (wheel), скачивание Qwen2.5 1.5B/3B/7B (+ uncensored)
├── C: FastAPI-сервер /content/thinking_server.py — /plan /plan/stream /reflect /chat
│     /chat/stream /dev /dev/stream /events /events/stream /models /model /health /metrics /dump
├── D: запуск llama.cpp :8001 + uvicorn :8000 + cloudflared (quick/named) + сторож
├── E: снапшот событий раз в минуту + keep-alive
└── F: остановка по THINKING_STOP=1
```

Транспортная цепочка: `панель → CLI-сервер (localhost) → client.py → trycloudflare.com → uvicorn :8000 → httpx → llama.cpp :8001`. Слабое звено — бесплатный туннель (рвёт молчащие соединения на ~120 с, «окна» тишины), под это построена вся стратегия: SSE с retry, запасной не-потоковый POST, предохранитель, прогрев.

## 4. Реестр находок

Severity: **[A] критический/высокий** (ломает заявленную функцию), **[B] средний** (надёжность/корректность в пограничных случаях), **[C] низкий** (качество/косметика/мёртвый код). Формат: файл:строка — описание, влияние, рекомендация.

### 4.1. Подтверждённые функциональные баги

#### AUD-01 [A] Экспорт и импорт памяти в панели падают с NameError
`tools/thinking_cli.py:791, 805` — в обработчике `/api/memory` (`act == "export"` и `act == "import"`) вызывается `utcnow()`, но функция **не импортирована** (импорты на строках 47–50 содержат только `ChatReply, MAX_MEMORY_FACTS, MAX_MEMORY_TURNS, SchemaError`).

Последствие: `NameError` внутри `do_POST`; `BaseHTTPRequestHandler` роняет соединение без ответа; панель показывает «Экспорт памяти не удался: …». Кнопки «Экспорт памяти»/«Импорт памяти» (заявленные в CHANGELOG commit `c22675d`) неработоспособны с момента их добавления.

Почему пропустили тесты: проверка `check('act == "export"' in cli_src …)` (`tools/thinking_test.py:811`) — строковая, обработчик никогда не вызывается.

Рекомендация: добавить `utcnow` в импорт из `thinking.schemas`; в тестах — вызывать обработчик (или вынести логику памяти в функцию и тестировать её).

#### AUD-02 [A] «Применить» в режиме «Разработка» записывает не тот код и не в тот файл
`tools/thinking_panel.html:1495–1511` — `devConfirmAnswer(kind)` берёт предложение модели в `devPending` (`p.filename`, `p.code`), но затем вызывает `devSave("model")` **без аргументов**: `devSave` (`:1340`) берёт имя текущего выбранного файла и содержимое textarea `#devcode`. Поля предложения модели (`p.code`, `p.filename`) молча отбрасываются.

Последствие: человек видит в диалоге подтверждения код модели (включая подпись «…применятся целиком»), нажимает «Применить» — а на диск пишется **прежнее содержимое редактора** под **именем текущего файла**. Для `action="create"` это ещё и не тот файл. Журнал при этом пишет «Применено: …» — вводит в заблуждение. Диалоговое окно подтверждения превращается в ложь.

Датировка: баг присутствует с первого релиза панели (`46dc4b3`, сравнение проведено по git) — `devSave` тогда имел сигнатуру `(source)`, позже появились `forceName/forceContent` (для автосохранения перед запуском, commit `515e0c7`), но вызов из подтверждения так и не передали `p.filename, p.code`.

Рекомендация: `devSave("model", p.filename, p.code)` (+ валидация имени через уже существующий `_safe_name` на стороне CLI). Немедленно добавить поведенческий тест/ручную проверку — это главная пользовательская ценность вкладки.

#### AUD-03 [A] `reflect --async` теряет результат: процесс завершается, не дождавшись фонового потока
`tools/thinking_cli.py:223–231` — `cmd_reflect` при `--async` запускает daemon-поток с `_do_reflect` и сразу возвращает 0. `main()` → `sys.exit()` убивает daemon-поток на середине HTTP-запроса.

Последствие: рефлексия «в фоне» на практике — выстрел вслепую: сокет закрывается, сервер (возможно) доделает генерацию и напишет события у себя, но клиентский `_record`, отчёт в reports.jsonl, статистика и код возврата теряются. Подсказка «результат: tail» показывает лишь события сервера, если те успели прийти. Заявленная функция не работает как задокументировано.

Рекомендация: либо убрать `--async` (честно), либо реализовать фон по-настоящему: отсоединяемый дочерний процесс (`subprocess.Popen` с записью результата в файл), либо минимум `th.join(timeout=…)` перед выходом.

#### AUD-04 [A] Тесты нарушают изоляцию: стирают реальную память пользователя и ходят в сеть
`tools/thinking_test.py`:
- `test_chat_memory_tokens` (строки 357–368) создаёт `make_client()` **без** `memory_path` → клиент пишет в реальный `logs/thinking/memory.json`: `remember("факт один")`, `remember("факт два")`, затем `forget()` — который стирает **все** факты и реплики пользователя. Текущий `memory.json` (96 байт, пустые списки) — следствие этих прогонов: любая память, накопленная через панель, уничтожается запуском тестов.
- `test_client` (строки 234–244) выполняет `set_url("https://example.invalid", "токен")` в TMP-конфиг, но **все последующие** `make_client()` читают этот же TMP-конфиг (`client_mod.LOCAL_PATH`): получают `base_url=https://example.invalid` и токен «токен». Дальнейшие вызовы реально Attempt сеть: в логе прогона видно `thinking POST /plan не прошёл ('latin-1' codec can't encode …)` — urllib не может закодировать кириллический токен в заголовок. Итог: «офлайн»-тесты делают сетевые попытки (замедляют прогон на ретраях) и зависят от содержимого TMP-конфига от прошлых прогонов.

Рекомендация: каждому `make_client()` — свой `memory_path`/`chat_path` в TMP (сделать их обязательными в `cfg` тестового клиента); после `set_url`-теста — удалять/подменять TMP-конфиг.

#### AUD-05 [B→A по частоте] Предохранитель один на SSE и REST: обрыв потока блокирует чат на 10 минут
`thinking/client.py:247–294, 581–615` — `_stream_loop` (SSE `/events/stream`) ходит через общий `_open`, где счётчик `_cb_errors` общий с REST. Пять подряд неудачных подключений SSE (например, туннель «мигает», а REST жив) открывают предохранитель на `breaker_pause=600 с` — и **все** вызовы, включая `/health`, `/chat`, `/dev`, получают мгновенный `ThinkingError("предохранитель…")`.

Это прямо противоречит собственному дизайну, зафиксированному в комментарии `client.py:609–611`: «обрыв SSE не должен объявлять субагента офлайновым — иначе панель мигает "НЕТ СВЯЗИ"». Онлайн-статус разделён, а транспортный канал — нет. С учётом задокументированных «окон тишины» туннеля (docs/ДИАГНОСТИКА_ПОТОКОВ.md §6) сценарий реален: минута плохого SSE → 10 минут полностью заблокированного субагента без единой попытки REST.

Рекомендация: отдельный счётчик/предохранитель для `/events/stream` (или не учитывать его ошибки вообще — поток и так переподключается с `reconnect_delay`).

#### AUD-06 [B] `plan_stream` невидим для метрик: успешный план через поток числится ошибкой
`thinking/client.py:357–405` — `plan_stream` (и путь `plan_with_fallback` → поток, `:549–553`) не вызывает ни `_record`, ни `_report_plan`, ни `stats["plans"]`. При этом предыдущая неудача `plan()` уже записана как `ok=False`.

Последствие: в «Диалоге»/«Выгоде» отражение успешного плана через поток — одна ошибка и ноль планов; отчёт во вкладке «Отчёты» не появляется; `tokens()` его не считает. Метрики врут в обе стороны (ошибки завышены, планы/шаги/токены занижены) — для проекта, который позиционирует «честный учёт», это заметная дыра.

Рекомендация: в конце успешного `plan_stream` вызывать тот же блок учёта, что и в `plan()` (`_remember_json` уже есть — добавить `_report_plan`/`_record`/`stats`).

#### AUD-07 [B] Двойной счёт fallback и фонового времени в долгоживущем процессе
`thinking/client.py:1504–1510` — `benefits(since="")`: `fb = (сумма fallback в inter) + self.stats["fallbacks"]`; аналогично `background_ms`. В долгоживущем процессе панели каждая запись есть и в `inter` (память+диск, дедуп по `_key`), и в `stats` → «за всё время» fallback удваивается. При `since` (сегодня) — корректно.

Рекомендация: считать только по `inter`, а `stats` использовать лишь как fallback при пустом журнале.

#### AUD-08 [B] Расхождение контекста модели: запуск и переключение используют разные `n_ctx`
`thinking/colab/cell_d_launch.py:109–114` — при старте `n_ctx = 8192 (GPU) / 4096 (CPU)`.
`thinking/colab/cell_c_server.py:936–945` (`_llm_cmd`, используется `/model` при переключении и сторожем) — `n_ctx = 4096 (GPU) / 2048 (CPU)`.

Последствие: после первого переключения модели из панели (или рестарта сторожем) на CPU контекст падает с 4096 до 2048 токенов — промт чата/плана с памятью и кодом (dev) может перестать влезать, качество деградирует без видимой причины.

Рекомендация: единая константа контекста (общий модуль/файл окружения), убрать дублирование строки запуска.

#### AUD-09 [B] Переключение модели: гонка «старый процесс ещё жив — ready отвечает он»
`thinking/colab/cell_c_server.py:962–982` — `_switch_to` делает `pkill llama_cpp.server`, `sleep(2)`, `Popen(новый)`, затем `_llm_ready()` стучит в `http://127.0.0.1:8001/v1/models`. Если старый процесс за 2 с не умер (большая модель выгружается дольше), ready возвращает **старый** сервер, файл `ACTIVE_MODEL_FILE` пишется, панель сообщает «переключено» — а новый процесс не смог занять порт и умер молча (лог в llm.log). Все alias одинаковы (`thinking`), поэтому отличить нельзя.

Рекомендация: после pkill ждать фактического освобождения порта (поллинг connect до отказа), проверять pid нового процесса (`proc.poll() is None`) и убивать по pid, а не по паттерну.

---

#### AUD-10 [B] Сторож ячейки D не умеет лечить «зависший, но живой» процесс
`thinking/colab/cell_d_launch.py:277–317` — при 3 неудачах `/health` сторож просто `Popen`-ит новый uvicorn/llama_cpp **без pkill старого**. Если старый процесс жив, но не отвечает (типичный зависший инференс), новый не сможет занять порт и умрёт; поломка сохраняется навсегда, при каждом цикле плодятся зомби-процессы.

Рекомендация: перед перезапуском гарантированно убивать процесс по pid, сохранённому при старте (`llm_proc.pid`, `api_proc.pid`), затем по паттерну, затем поднимать.

---

#### AUD-11 [B] Неограниченные очереди подписчиков SSE — утечка памяти на сервере
`thinking/colab/cell_c_server.py:661–677` — на каждое соединение `/events/stream` создаётся `asyncio.Queue()` без `maxsize`; `emit()` кладёт события через `put_nowait`. Если клиент (или Cloudflare-прокси за ним) перестал читать, но соединение не закрыто, очередь растёт неограниченно. `MAX_EVENTS` ограничивает только `deque` истории. За сутки «тихого» зависшего соединения при активном использовании — сотни МБ.

Рекомендация: `asyncio.Queue(maxsize=200)` + при `QueueFull` — закрывать подписчика (он всё равно отстал), либо отслеживать `qsize()` и отсоединять.

---

#### AUD-12 [B] Клиент не валидирует ответы сервера по собственному контракту
`thinking/client.py:329–352` — `plan()` возвращает сырой dict от сервера без `Plan.from_dict`. `schemas.py` объявлен «единственным источником правды», но применяется только в тестах и на сервере. Старый/сломанный сервер может вернуть структуру без `steps` — она уедет в `plan_with_fallback` как «успех» и упадёт уже в вызывающем коде (или в `_print_plan`). Аналогично `_chat_via_plan` не проверяет план.

Рекомендация: в `plan()`/`reflect()` прогонять ответ через `Plan.from_dict`/`ReflectResponse.from_dict` с мягкой нормализацией (как `coerce_plan` на сервере) — и это же закроет AUD-06-подобные дыры учёта.

#### AUD-13 [B] Режим «Разработка» отправляет код без проверки на секреты
`thinking/client.py:1065–1076` — `_dev_body` вызывает `_check_secrets` только для текста запроса; `active_code` (до 8000 символов реального файла) и список `files` уходят на сервер без `has_secret`. При этом `_check_secrets` для **текста** работает наоборот слишком строго: сообщение «поменяй строку token = os.getenv(...)» будет **заблокировано** (ложное срабатывание `SECRET_RE` на `token = os.getenv`), а реальный секрет в коде файла — отправлен.

#### AUD-26 [C] Модель крупнее RAM отвергается вслепую (найдено на живом прогоне 04.10)

Прогон `PROFILE = "big"` (Qwen3-30B-A3B, 17.3 ГБ при RAM 12.6 ГБ) дал три ошибки, которые не видны в коде:

- **Бюджет считался по первой кандидатуре.** Модель не поднялась, ячейка откатилась на 3B — а лимиты остались от 30B (`1200/2400/3000` вместо `700/1400/2000`). Пересчёт теперь после выбора модели и без `setdefault` (который тихо оставил бы прежнее значение).
- **Времени ожидания не хватало.** `wait_http(tries=45, gap=2)` = 90 с на любую модель; 17.3 ГБ с диска читаются дольше. Теперь `45 + ГБ × 12`.
- **Причина отказа была не видна.** `/content/llm.log` содержал только строку команды — ни строки ошибки. Из этого нельзя было отличить нехватку памяти от незнания архитектуры (Qwen3 требует сборки llama.cpp 2025 года). Теперь читается код возврата: `-9` OOM-киллер, `-11` segfault, `>0` свой код, `None` процесс жив; ячейка A печатает версию движка.

Плюс два следствия:

- **Запасная модель профиля `strong` была того же размера, что и основная** (Coder-14B, 8.4 ГБ) — то есть откат не мог спасти сессию при нехватке памяти, а качать её пришлось бы зря. Запасная теперь 3B. Проверяется тестом для всех профилей.
- **Ячейка F отказывалась останавливать субагент через `SystemExit(0)`.** IPython внутри ячейки принимает `SystemExit` за просьбу выключить ядро, поэтому каждый «Run all» печатал «An exception has occurred» и «To exit; use 'exit', 'quit'...». Поведение было правильным, вид был аварийный.

Итог для 30B на бесплатном Colab: при 12.6 ГБ RAM надёжный путь — `strong` (8.4 ГБ весов + ~0.8 ГБ KV), а `big` остаётся ставкой на T4 с большей памятью.

## 5. Сильные стороны

1. **Дисциплина зависимостей.** Весь ПК-стек — чистая стандартная библиотека (urllib/http.server/threading). Подсистему реально скопировать в любой проект одним каталогом, конфликтов нет. Обоснование зафиксировано в ТЗ и соблюдено.
2. **Многоуровневая деградация.** Путь отказа продуман на каждом слое: ретраи с экспонентой → повтор по потоку при 524 → запасной не-потоковый POST → локальная заглушка с честным `source="local-fallback"` и `confidence=0.0` → приложение продолжает работать. Ни одно исключение субагента не роняет основное приложение (кроме осознанного `SchemaError` на секретах).
3. **Инженерия вокруг ненадёжного транспорта.** Диагностика SSE-обрывов с хронологией, `--protocol http2` против маленьких UDP-буферов QUIC, stall-таймаут 75 с под TTFT 60–80 с на CPU, прогрев `/health` раз в ~25 мин, предохранитель против спама ретраями (пусть и с багом AUD-05). Это редкий пример проекта, который **измерил** свой транспорт и построил фиксы по уликам из журналов.
4. **Атомарная запись и ограниченные буферы.** Все JSON-файлы пишутся через `.tmp` + `replace`; журналы ротируются; списки в памяти обрезаны. Систему сложно положить переполнением.
5. **Контракты со снимком схемы.** `docs/schema_plan.json` сверяется тестом — правка полей без правки снимка валит CI. Двухуровневая валидация (структурная ошибка → отбраковка, косметика → нормализация) — правильный подход к слабым моделям.
6. **`coerce_plan`/`guard_reply`/`plan_data` — работа с «глупыми» моделями.** Вместо 502 на не-JSON маленькие модели получают мягкое приведение (строка→список, `"s1"`→id, текст→план из одного шага). Счётчики `bad_json`/`plain_text` честно показывают деградацию формата.
7. **Честность как принцип.** Оценка токенов помечается `tokens_estimate`, `usage_exact` на сервере, «доля успешных ответов» в панели, панель «Чего он не делает». Ложь в UI найдена только в баге AUD-02 (непреднамеренно).
8. **Режим «Разработка» с контролем человека.** Песочница, белый список имён, откаты (20 последних на файл) в `.rollback`, журнал каждого действия, подтверждение изменений, запуск с таймаутом и utf-8. Модель не касается файлов сама — применение всегда за человеком (сам контроль и подвёл из-за AUD-02, но каркас правильный).
9. **Память с дедупликацией и саммари.** Точные дубли не пишутся, пересекающиеся факты сливаются в более полный, выпавшие из окна реплики сжимаются в одно саммари-факт ≤300 знаков; экспорт/импорт с лимитами схемы (кнопки, правда, сломаны — AUD-01).
10. **Документация.** README на 15 разделов, отдельная дока диагностики потоков с датами и версиями, план развития с приоритетами и готовым/бэклогом, CHANGELOG, быстрый старт, ТЗ. Документация обновляется вместе с кодом (расхождений почти нет — см. AUD-25 про plan_timeout).
11. **CI с матрицей.** Ubuntu (3.12/3.14) + Windows (3.14), фикс CRLF через `.gitattributes`, PYTHONUTF8 для кириллицы — типовые грабли разъёта локалей уже закрыты и задокументированы.
12. **Идемпотентные ячейки Colab** (A: не качает повторно, D: убивает старые процессы, F: защита от «Run all» через THINKING_STOP) и сборщик ноутбуков из исходников ячеек (`build_colab.py`) — источник правды один.

## 6. Слабые стороны (систематизация)

1. **Тесты проверяют текст, а не поведение.** Из ~325 проверок большинство — `check("маркер" in исходник)`. Так прошло: AUD-01 (utcnow), AUD-02 (devConfirmAnswer — JS вообще не исполняется тестами), AUD-25 (`or True`). Бихевиористически покрыты только фолбэки клиента, кэш, память, удаление, dev-файлы. **Сервер FastAPI не исполняется ни одним тестом** (только grep по его тексту) — все regressions сервера невидимы до живого Colab.
2. **JS панели — непротестируемая зона.** 1 200 строк логики (стрим, подтверждение, рендер, кэш-совместимость) без единого модульного теста. Самые дорогие баги проекта (AUD-02, AUD-15) живут именно там.
3. **Дублирование клиент↔сервер.** `extract_json`, `SECRET_RE`, `redact`, `utcnow`, схемы полей продублированы в `cell_c_server.py`. Обоснование (самодостаточная ячейка) валидно, но расхождения уже начались; нужен автоген или тест-сверка.
4. **Глобальное изменяемое состояние.** `_ANSWER_CACHE` на уровне модуля, `health_data` класса, `stats` без блокировок при многопоточном HTTP-сервере панели (`ThreadingHTTPServer` + общий `client`) — корректность держится на GIL и везении.
5. **Нет файловых блокировок.** Панель, CLI и тесты пишут одни файлы (`memory.json`, JSONL) — потери записей при параллельной работе (AUD-16) и «тест стирает пользовательские данные» (AUD-04).
6. **Честность метрик неполна.** plan_stream вне учёта (AUD-06), двойной счёт (AUD-07), фиктивные токены заглушек (AUD-22), стриминговые чаты без токенов.
7. **Транспорт — единственный и хрупкий.** Один quick-туннель (случайный адрес, «окна» тишины, 120-с лимит). Именованный туннель поддержан, но не дефолт. Нет health-мониторинга со стороны ПК, который бы отличал «туннель умер» от «Colab уснул» (doctor делает это вручную).
8. **Секретность с дырами.** `?token=` в URL, CORS `*`, `active_code` без `has_secret`, токен в `/api/state` (AUD-13/17/21).
9. **Сторож и переключение моделей лечат не все режимы отказа** (AUD-09/10) — «живой, но зависший» процесс не восстанавливается, а молча плодит дубли.
10. **Скорость CPU-инференса** (1–3 ток/с) делает развёрнутые ответы минутными; бюджеты токенов приходится ужимать по модели (260–800). Это ограничение платформы, но часть UX-ценности (живой диалог) на CPU реализуется плохо — и проект честно это показывает в подсказках.

## 10. Как искать больше багов (методика + инструменты)

### 10.1. Статический анализ (дёшево, внедрить за вечер)
```bash
pip install ruff mypy bandit
ruff check thinking tools scripts            # линт: найдёт мёртвый код (AUD-20), unused import secrets
mypy thinking/                               # client.py уже с аннотациями —类型 пограничные места всплывут
bandit -r tools thinking -ll                 # безопасность: query-string токен, subprocess без shell=False-проверок
```
Добавить в CI отдельным шагом (не валить, а предупреждать → потом валить). Ruff с правилами `B` (bugbear) нашёл бы `or True` в тесте (AUD-25) и `except Exception: pass` без логирования.

### 10.2. Property-based тесты (Hypothesis) — для парсеров и нормализаций
Цели: `extract_json`, `redact_secrets/has_secret`, `_norm_fact`, `_summarize_turns`, `estimate_tokens`, `ChatReply.from_dict`:
```python
from hypothesis import given, strategies as st
@given(st.text())
def test_extract_json_never_crashes(s):  # любые входы — только ValueError или корректный dict
    try: extract_json(s)
    except ValueError: pass
```
Гарантированно найдутся краши на неожиданных входах (вложенные кавычки, `\u`-экранирование, очень глубоки JSON) — именно там, где живут ответы слабых моделей.

### 10.3. Мутационное тестирование — вскрывает фальшивые проверки
```bash
pip install mutmut
mutmut run --paths-to-mutate thinking/schemas.py --tests-dir tools/
```
Мутант, который выживает = проверка, которая не проверяет. Для этого проекта сразу покажет, что большая часть «строковых» тестов не убивает мутантов — и превратит AUD-25-подобные `or True` в явный список долгов.

### 10.4. Поведенческие тесты панели (Playwright) — зона с самыми дорогими багами
Поднять `thinking_cli.py panel` против мок-клиента (см. 10.5) и писать сценарии: «отправить сообщение → пришёл token-поток → done», «получить предложение → нажать Применить → файл на диске содержит код модели» (убил бы AUD-02), «ввод факта живёт дольше 3 секунд» (AUD-15), «экспорт памяти не падает» (AUD-01). Скелет: `pytest-playwright`, headless chromium, `page.fill("#chatinput", ...)`.

### 10.5. Интеграционный стенд с мок-сервером Colab (локальный, офлайн)
Написать `tests/mock_server.py` на `http.server`: сценарии «health ok», «/chat 404 (старый сервер)», «SSE обрыв на середине», «stall 80 с потом токены», «мусорный JSON», «429». Поведенчески покрыть: `_stream_read` (ретраи, бюджет, done), `chat_stream → /chat` фолбэк, `dev → /dev` фолбэк, breaker (открытие/закрытие/сброс), `_looks_like_missing_route`. Это локализует все транспортные фиксы, которые сейчас проверяются только «в бою».

### 10.6. Юнит-тесты FastAPI-сервера без Colab
`cell_c_server.py` почти тестируем как есть: `from fastapi.testclient import TestClient`, мок `chat_json_usage`/`chat_stream` (monkeypatch), проверка эндпоинтов: авторизация (401/429), `coerce_plan`/`guard_reply` на кривых ответах LLM, `/models`/`/model` (мок `subprocess.Popen`), лимиты очередей. `%%writefile`-строку обходить импортом файла напрямую (`importlib.util.spec_from_file_location`, как уже сделано в `_load_cli_module`). Это закроет самый большой нетестируемый кусок системы.

### 10.7. Лог-мининг собственных журналов (данные уже собираются!)
Скрипт-инвариантник `tools/check_logs.py`: по `logs/thinking/*.jsonl` проверять — rid уникальны; `seq` мыслей монотонный; у записи `ok=False` есть `summary` с причиной; чат из `chat.jsonl` имеет парную запись в `interactions.jsonl`; `duration_ms` в разумных пределах; доля fallback по дням (график деградации туннеля). Запускать в CI на фикстурах и локально на живых логах — баги вроде AUD-06/07 (расхождение учёта) находятся автоматически.

### 10.8. Гонки и параллелизм
- `ThreadSanitizer` недоступен для Python — заменить целевыми стресс-тестами: 10 потоков `remember_turn` + 10 `memory()` → проверка, что ни одна реплика не потерялась (сейчас потеряется — AUD-16).
- Процессы: параллельно `thinking_cli.py plan` и панель → проверка целостности JSONL (последняя строка валидна после любой интерливенции).
- Сервер: 5 конкурентных `/chat/stream` при `CONCURRENCY=1` — семафор держит, но проверить, что 4-й не получает 429 от общего rate-limit (AUD-14).

### 10.9. Fuzzing транспорта
Скормить `_stream_read` и `plan_stream` битые SSE-потоки: `data:` без JSON, UTF-8 разрезанный посреди многобайтового символа (реально при chunked-туннеле!), `event: done` без данных, несколько `data:` в одном блоке. Разрезанный UTF-8 — вероятный реальный баг: `resp` итерируется по строкам, `decode("utf-8","replace")` на строке, разрезанной по байтам, даст «�» внутри русских слов.

### 10.10. Процедура «как чинить найденное» (уже доказала себя в проекте)
Проект уже использует правильный цикл: воспроизвести по журналу → датировать по git → написать регрессионный тест (примеры: rid-удаление, dev-путь, «первый токен позже stall» в docs). Рекомендация — формализовать: каждый баг из этого аудита получает (1) регресс-тест, воспроизводящий поведение, (2) фикс, (3) строку в CHANGELOG со ссылкой на тест. Для AUD-01/02/03 тесты пишутся за минуты и навсегда закрывают класс «строковые тесты пропустили регрессию».
